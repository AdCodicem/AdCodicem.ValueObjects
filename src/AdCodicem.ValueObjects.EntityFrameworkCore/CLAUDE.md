# AdCodicem.ValueObjects.EntityFrameworkCore

User-facing behaviour: `website/docs/how-to/ef-core.md`. Tests: `Persistence/` of the unit suite (models built on Npgsql,
which opens no connection, and SQLite in memory), the integration suite on PostgreSQL and SQL Server, the compiled model
of `tests/NativeAot`, and EF Core 11 in the island.

## Built against EF Core 10, run under 11

- Never call `IConventionPropertyBuilder.SetElementType` nor implement `IPropertyElementTypeChangedConvention`: EF Core 11
  removed both, so a package built against 10 would throw `MissingMethodException` or `TypeLoadException` and fail every
  model `ConfigureValueObjects` builds. `ValueObjectCollectionConvention` marks a primitive collection through
  `IConventionProperty.SetElementType` when an entity type or a complex property is added, and configures the elements
  as the model finalizes, which also reaches a collection the application declares.
- Every suite runs EF Core 10: only `tests/Compat` notices such a break.
- An element of `TSelf?` over a value type takes the converter of `TSelf`, never a nullable one: EF Core's JSON writer
  throws a `NullReferenceException` on the `null` a nullable converter hands it. Such an element is refused where an
  optional column stores `NULL`, and over text it is stored as a JSON `null`.

## Conventions and the registry

- `ConfigureValueObjects`, `ConfigureEntityIds` and the CHECK constraint convention resolve through the registry and close
  adapters through visitors; the CHECK convention finds the value object a converter of the package maps
  (`ConverterTypes.TryGetValueObjectType`, over `ConverterTypes.Definitions`) through `TryResolve`. A generic value object
  registers its definition: the convention maps the definition and closes the converter per property. The one runtime-closing exception: the converter of a `TSelf?` property, or of such an
  element of a collection over text, is closed with `MakeGenericType` (`ConverterTypes`) and created with
  `Activator.CreateInstance` (`GenericValueObjectConvention.PropertyConversion.Visit`), because C# names it only under
  `TValue : struct` or `TSelf : IValueObject<TSelf, string>`, which `Visit` cannot prove, and it must stay the exact type a
  compiled model names. No convention runs under native AOT, where EF Core reads the compiled model.
- Column sizing reads the **descriptor's** `Schema`, which a registration made by hand may set apart from the type's,
  handed to the visitor in a field; the CHECK constraint convention reads **`TSelf.Schema`**, since a constraint must be no
  stricter than `Validate`. Do not swap them.
- The key convention closes nothing: it tells a value object over `Guid` by `IValueObject<Guid>` and names a factory that
  is not generic. `ConfigureEntityIds` visits the identifier's `ValueObjectDescriptor` from `TryResolve`, its visitor
  casting itself to an interface over `string`; an identifier registered with `EntityIdRegistry` alone, by hand, is
  described by reflection there and stays in `ValueObjectRegistry`.
- `ConfigureValueObjects(strict: true)` validates on read; the converter refuses the write of a refused value (a default
  instance) with `ValueObjectException` either way.

## Keys (`HasValueObjectKeyGeneration`, `ValueObjectKeyConvention`)

- EF Core makes a key generated on add from the key's own CLR type, so a key typed as a value object is generated by
  nothing, and `ValueGeneratedOnAdd()` alone gets random GUIDs, or temporary integers a strict converter refuses.
- A generated GUID goes through `Create`, since a write validates only an instance equal to the default; a temporary
  integer goes through `CreateUnchecked`, the database replacing it.
- EF Core calls a property's generator whenever it has one, even at `ValueGenerated.Never`, for an entity whose key equals
  its sentinel, in `Add`, `Attach`, `Update` and `Remove`: `ValueObjectKeyConvention` installs
  `UnassignedValueObjectKeyGenerator`, which refuses an unset `Guid` key (`value_object.required` under
  `ValueObjectErrors.ErrorCodeKey`) without changing the column or the migration snapshot. Consequences (`HasData` of a
  `Guid.Empty` key fails; `Attach` takes a dependent whose foreign key was left at its default as new) are in the guide
  and the changelog: keep them in step.
- EF Core caches one generator per property in its internal service provider, which serves one provider:
  `ProviderGuidValueGenerator` reads the provider's name once.
- `ValueObjectKeyGenerator` refuses a temporary integer on a provider that is not relational, which would store it as the
  key; `Microsoft.EntityFrameworkCore.InMemory` is a test-only reference for that check.
- `HasValueObjectKeyGeneration` is declared once per underlying type, each in a static class of its own (`Guid` in
  `ValueObjectConventionExtensions`; `ValueObjectInt16KeyGenerationExtensions`, `…Int32…`, `…Int64…`): C# refuses two
  methods differing only by their constraints in one class (CS0111) and drops a candidate whose constraints fail, so the
  call needs no type argument. Add an integer type only if SQL Server and PostgreSQL make its identity column of the
  type's own width.

## The `.Value` translator (`UseValueObjectQueries()`)

- Query services cannot come from `ConfigureConventions`: `ValueObjectQueryOptionsExtension`, an
  `IDbContextOptionsExtension`, registers `ValueObjectMemberTranslatorPlugin`, which hands EF Core
  `ValueObjectMemberTranslator`. It asks no registry: it tells a property by the converter on the SQL expression.
- It answers `.Value` only for one of the six converters of `ConverterTypes.Definitions`, alone or composed by EF Core with
  its own conversion. `CompositeValueConverter` is internal, so it reads `ConvertToProviderExpression`: where the mapping
  `FindMapping(TValue, storeType)` carries no converter, the conversion must be the call to the package converter's
  `ToProvider` alone, since one written around it is the application's (`ComposeWith`), which may store something else;
  where the provider converts the type itself, a call to it anywhere will do.
- It re-types a column EF Core links to its table (`ColumnExpression.Column` set) or a `JsonScalarExpression`; anything
  else (a table-valued function's element, a column an optional navigation joins in, a `COALESCE`, a `CASE`) gets a
  `CAST` to the same store type. Never cast a table's column: SQL Server then scans its index. Npgsql infers an `unnest`
  array's mapping from the columns referencing its element and fails on a re-typed one (`ArgumentException` inside a
  `TargetInvocationException`), which the unit suite's Npgsql text pins. EF Core 11 leaves the no-op casts out.
- A translated, projected `.Value` is read from the column as SQL reads it, which a strict context does not validate.
- `dotnet ef dbcontext optimize --precompile-queries` bakes the translator's SQL in: the design-time options must call
  `UseValueObjectQueries()` too, or the precompilation fails on that query.
- EF Core adds an extension's services only to a service provider it builds, never to one `UseInternalServiceProvider`
  names, and runs `Validate` before such a provider's singleton options are set: `Validate` refuses a provider lacking
  the mark `ApplyServices` adds and resolves nothing else, since resolving the plugin would build Npgsql's type mapping
  source too early.

## CHECK constraints (`AddValueObjectCheckConstraints`, `UseValueObjectCheckErrors()`)

- The convention writes `MinLength`, the bounds, the closed sets and, opted in (`ValueObjectCheckOptions.Patterns`), the
  pattern, the maximum length staying the column size, only where the database refuses no value the type accepts: a rule
  is left out for a length in bytes, a column comparing apart from .NET, a closed set of text whose type stores another
  spelling of a known value (`KnownValueSpellings`), a column two types of a hierarchy share for two value objects; no
  pattern on a fixed-length column.
- `SqlPattern` writes PostgreSQL's `~` and SQL Server 2025's `REGEXP_LIKE` from the shared pattern tree; it fails the
  model on a pattern the dialect reads apart unless `ExcludePattern<TSelf>()`, and on repetitions matching more than 1000
  characters once written out, which both engines refuse as too complex only when they first check a value.
- A name is `CK_…_{rule}`, with an `_[0-9A-F]{8}` hash of table and column when the provider would cut it, another check
  constraint of the model holds it already (in its table or, on SQL Server, in its schema), or, on SQL Server, another
  table of the schema would take it. The code is read back **off the name, never off the model**: `CheckConstraintRules`
  and the reader share the rule words (internal constants of `ValueObjectCheckConstraints`), and a unit test reads every
  name the convention writes back to its rule. A new rule goes in both.
- `ValueObjectCheckErrorInterceptor` must stay both `IDbCommandInterceptor` and `ISaveChangesInterceptor`: EF Core calls
  `CommandFailed` only around `DbCommand.Execute*`, and an error raised while `ReaderModificationCommandBatch` consumes
  results (a later statement of a batch, `RETURNING` or `OUTPUT INSERTED` reading back a key, SQL Server's multi-row
  `MERGE`, `UPDATE … OUTPUT 1`) reaches only `SaveChangesFailed`, inside the `DbUpdateException`
  (dotnet/efcore#35229).
- No interceptor sees an error raised while a query's rows are read: on SQL Server, `SqlQueryRaw` or `FromSqlRaw` over
  `OUTPUT` fails with 547 and no code, which the guide states and `ValueObjectCheckConstraints.TryGetCode` reads;
  PostgreSQL's and SQLite's `RETURNING` fail as the command runs.
- Read a code only off an error reporting a violated CHECK constraint, or a migration's "There is already an object
  named …" would get one: PostgreSQL's SQL state `23514` (Npgsql names the constraint in `Data["ConstraintName"]`),
  SqlClient's `Data["HelpLink.EvtID"] == "547"`, set in every language, the name read off a token of the message, SQLite's
  `CHECK constraint failed: `, never translated. A token ends at white space or a quotation mark and loses the sentence's
  punctuation: SQL Server's Czech and Dutch messages leave the name unquoted, followed by a full stop.
- EF Core logs a failure before it calls the interceptors, and builds the event data of every command once any command
  interceptor is registered (about 0.8 KB per query on SQLite), which the guide states.
