## Remarks

<p>
<code>XmlSerializer</code> and <code>DataContractSerializer</code> then write a value object as its underlying value, in the form
<code>XmlSerializer</code> writes that type in, and read it back through its rules: a value the type refuses fails the read
with an <xref href="System.Xml.XmlException" data-throw-if-not-resolved="false"></xref> carrying the rule's code under <xref href="AdCodicem.ValueObjects.ValueObjectErrors.ErrorCodeKey" data-throw-if-not-resolved="false"></xref>.
Without it, both write an empty element and read back a default instance.
</p>
<p>
The schema each serializer exports describes the value object as an <code>xs:simpleType</code> restricting the XSD type of
its underlying value, with its rules as facets.
</p>
<p>
It covers the value objects and the entity identifiers the generator writes in the assembly, but one that implements
<xref href="System.Xml.Serialization.IXmlSerializable" data-throw-if-not-resolved="false"></xref> or declares a schema provider itself, whose implementation
stands. A project file sets it with an <code>AssemblyAttribute</code> item whose <code>Include</code> is the full name of this
attribute, which the SDK writes into the assembly's attributes.
</p>

## Properties

### Namespace {#AdCodicem_ValueObjects_Annotations_ValueObjectXmlSerializationAttribute_Namespace}

Gets or sets the XML namespace of the schema types the value objects are described with.

```csharp
public string? Namespace { get; set; }
```

#### Property Value

 [string](https://learn.microsoft.com/dotnet/api/system.string)?

#### Remarks

<p>
<a href="https://learn.microsoft.com/dotnet/csharp/language-reference/keywords/null">null</a>, the default, stands for the namespace <code>DataContractSerializer</code> derives from the CLR
namespace of each type, which it resolves against http://schemas.datacontract.org/2004/07/ as a relative URI.
</p>
<p>
A schema type is named after its value object, without the CLR namespace, so a namespace set here puts the value
objects of every CLR namespace of the assembly side by side: two of the same name then share one schema type, and
the schema provider refuses the second with an <xref href="System.InvalidOperationException" data-throw-if-not-resolved="false"></xref> when their rules differ,
rather than describe it with the rules of the first. Give such value objects distinct names, or leave this unset.
</p>
